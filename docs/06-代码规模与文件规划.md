## 4. 规模控制策略

### 4.1 达到下限（> 2000 行）的手段

1. **核心算法完整实现**：滑动窗口的惰性轮换、直方图 P95、探测调度等均为实质逻辑，天然产生足量代码。
2. **注释与文档化代码**：每个公开符号写 Doc 注释（Go 规范要求），按 22 个文件 × 平均 12 个公开符号估算约贡献 260 行。
3. **HTTP API 完整实现**：4 类监控接口 + 4 类管理接口 + 3 类演示接口，handler 与序列化代码充实。
4. **配置校验**：逐字段校验函数（`Validate`）与部分更新合并逻辑。

### 4.2 控制上限（< 2200 行）的手段

1. **拒绝过度设计**：不引入插件体系、持久化、Prometheus 导出、grpc 等超出需求的功能。
2. **合并小文件**：若实现过程超出预算，优先合并 `window.go`（接口）与 `sliding_window.go`、`result.go` 与 `errors.go`，保证文件数仍 > 20。
3. **控制样板代码**：API 模型字段复用 `Snapshot` 而非重复定义 DTO；handler 用共享的 JSON 响应辅助函数。
4. **每文件预算即红线**：编码时以本表为基准，偏差 ±10% 以内，超出的文件拆出辅助函数到既有文件或削减注释。

### 4.3 行数度量与校验方法（CI/本地脚本）

```bash
# 统计 Go 代码文件数
find . -name '*.go' ! -name '*_test.go' | wc -l

# 断言：2115 ± 容差 80 行（即 [2035, 2195]）且文件数 ∈ (20, 25)
```

## 6. 规模风险与应对

| 风险 | 应对 |
| --- | --- |
| 实现后行数不足 2000 | 按 §4.1 手段扩充：补充注释、完善事件负载、增加管理接口字段 |
| 实现后行数超 2200 | 按 §4.2 手段收敛：合并文件、精简注释、复用序列化逻辑 |
| 文件数超 24 | 合并 middleware 两文件 / server 的 metrics 并入 handlers |
| 文件数不足 21 | 将 fallback 拆分降级策略 + 执行器；或将 server 的 api_models 拆分 |
| 统计口径分歧 | 以"非空行、不含注释"为准，最终以实际 `wc -l` 与校验脚本结果为准 |
